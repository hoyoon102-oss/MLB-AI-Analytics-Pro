# Version 4.8 — 데이터베이스·캐시·성능 보고서

## 1. 점검과 안전 조치

기존 `services`, `analytics`, `components`, `utils`, `scripts`, `tests`, `translations`, `data` 구조를 검토했습니다. MLB API 호출은 선수 검색·프로필·성적·리그·시즌·커리어·리더보드 서비스에, Baseball Savant CSV 호출은 Statcast 서비스에 모여 있었습니다. 기존에는 주로 Streamlit 메모리에만 저장하여 프로세스를 종료하면 캐시가 사라졌습니다. 리더보드는 이미 전체 페이지 검증 후 로컬에서 필터링하며, Statcast는 선택 선수·날짜 범위를 나누어 조회하고 투구 중복을 제거합니다. 이 동작과 계산식은 유지했습니다.

실행 계획은 ① 원본 백업 ② 별도 SQLite 계층 ③ 검증된 서비스 결과 연결 ④ 상태 표시·관리 도구 ⑤ 테스트·비교 측정이었습니다. 변경 전 코드는 `.backups/v48-before-20261105-143249`에 복사했습니다. `start.bat`, `data/favorites.json`, `data/settings.json`이 백업본과 바이트 단위로 같은 것도 확인했습니다. 가상환경은 변경하지 않았습니다.

## 2. 새 구조와 파일

요청 흐름은 **Streamlit 메모리 → SQLite → 기존 API 서비스**입니다. 외부 요청·검증·통계 계산을 새로 만들지 않고 기존 서비스 함수가 정상 반환한 결과를 저장합니다. 반환값의 정수 키·튜플·집합·빈 값도 재시작 후 그대로 복원합니다. JSON 인코딩을 사용하며 pickle은 사용하지 않습니다.

새 파일:

- `services/database.py`: 연결, 스키마 버전, 인덱스, 트랜잭션, 무결성 검사, 백업, 확인 후 캐시 삭제.
- `services/cache_manager.py`: 영구 캐시, 반환 형식 보존, 메모리 적중 관찰, 현재 화면 출처 정보.
- `services/cache_policy.py`: 데이터 종류·시즌별 TTL 설정.
- `analytics/performance_monitor.py`: 프로세스별 실제 관측치.
- `components/system_performance_ui.py`: 한·영 상태 표시와 개발자 관리 화면.
- `scripts/benchmark_cache.py`: 임시 DB와 별도 프로세스를 사용하는 재현 가능한 비교 측정.
- `tests/test_database_cache.py`, `tests/test_system_performance_ui.py`: DB·캐시·관리 화면 테스트.
- `docs/v48-benchmark.json`, `docs/v48-startup-benchmark.json`: 측정 원자료.

연결을 추가한 기존 파일은 선수 성적·검색·프로필, 리그 평균, 커리어, 리더보드, Statcast 서비스와 `components/awards.py`입니다. `components/dashboard.py`에 버전·관리 화면·새로고침 연결을 추가했고 `components/ui_components.py`의 버전 표기와 README를 갱신했습니다. 통계 계산 모듈, 테마 CSS, 번역 카탈로그, 런처는 변경하지 않았습니다.

## 3. DB 위치와 스키마

Windows 기본 위치는 `%LOCALAPPDATA%\MLB-AI-Analytics\mlb_analytics.db`입니다. 프로젝트가 OneDrive Desktop에 있으므로 새 쓰기용 DB는 기본적으로 동기화 폴더 밖에 생성합니다. 첫 실제 데이터 요청 때 디렉터리·DB를 생성합니다. Windows 외 환경은 `~/.local/share/MLB-AI-Analytics`를 기본으로 사용합니다.

`MLB_ANALYTICS_DB_PATH`로 별도 위치를 지정할 수 있습니다. 이 설정은 기존 DB를 이동하거나 가져오지 않습니다. 이전 DB를 사용하려면 앱을 종료하고 검증된 백업을 복구해야 합니다. `MLB_ANALYTICS_DATA_DIR`는 기존 JSON 위치 설정으로 계속 사용하며 DB 위치와 분리했습니다.

SQLite 내장 라이브러리만 사용합니다. 연결은 작업마다 열고 닫으며 공유하지 않습니다. WAL 대신 DELETE journal, 외래키 검사, 10초 잠금 대기와 쓰기 트랜잭션을 사용합니다. `PRAGMA user_version=1`로 스키마 버전을 관리하고, 지원 버전보다 높은 DB는 쓰지 않습니다. 초기 스키마 작성도 하나의 명시적 트랜잭션입니다.

- `players`: MLB ID, 이름, 포지션, 타격·투구 손, 데뷔일, 원본 메타데이터, 갱신 시각.
- `teams`: 팀 ID·시즌 복합 키, 이름, 약어·리그용 필드, 메타데이터. 기존 팀 목록이 제공하지 않는 약어·리그는 임의로 채우지 않습니다.
- `datasets`: 서비스·인자 기반 고유 키, 시즌, 선수 ID, 범주, 경기 범위, 출처, 구조화 결과, 수집 시각, 만료 시각, 완료 표시. 선수 시즌 성적·리더보드·Statcast·커리어는 이 공통 테이블에서 구분합니다. 동일 인자는 중복 행 대신 갱신합니다.

범위·만료 인덱스를 두고 조회는 고유 키로 처리합니다. 리더보드 키에는 시즌·타자/투수·자격 모집단 등이 포함됩니다. 기존 전체 모집단·자격·이적 소속 검증과 로컬 순위·필터 계산을 유지합니다.

## 4. 기존 사용자 데이터

**즐겨찾기·언어·맞춤 필터 프리셋은 SQLite로 이전하지 않았습니다.** 현재 원자적 JSON 저장이 이미 구현되어 있고, 성능상 필요가 없어 변경 위험을 줄였습니다. 원본 파일은 보존했고 변경 전 백업에도 포함했습니다. DB 캐시 삭제는 이 JSON에 접근하지 않습니다. 프리셋 파일은 존재할 때 기존 저장 코드를 그대로 사용합니다. 따라서 사용자 설정에 대한 별도 마이그레이션·롤백 단계는 필요하지 않습니다.

## 5. 캐시 정책·실패 동작

| 자료 | SQLite 기본 보관 시간 |
|---|---:|
| 이전 연도 시즌 성적·리더보드·Statcast | 30일 |
| 현재·미래 연도 시즌 자료 | 15분 |
| 프로필·팀 메타데이터·수상·시즌 달력 | 24시간 |
| 연도 인자가 없는 검색·커리어·연도별 이력 | 15분 |

현재 연도는 시즌 종료 여부를 확정하지 않고 보수적으로 짧게 유지합니다. 미래 연도도 짧게 처리합니다. 정규시즌·포스트시즌의 구분은 캐시 키와 범위에 포함하며 기존 서비스는 계속 정규시즌을 요청합니다. 수상 이력은 별도 범위입니다.

환경변수 `MLB_CACHE_TTL_HISTORICAL`, `MLB_CACHE_TTL_METADATA`, `MLB_CACHE_TTL_ACTIVE`로 초 단위 조정할 수 있습니다. 최소 900초입니다. 연결한 서비스의 메모리 TTL은 60초이며, SQLite 항목의 남은 유효기간이 65초 이하이면 재조회하여 메모리에 만료 직전 자료를 넣지 않습니다. 기존 외부 서비스의 타임아웃, Statcast의 제한된 재시도·속도 제한을 유지했습니다.

불완전한 리더보드는 기존 검증에서 예외를 발생시켜 저장하지 않습니다. 누락된 선수 성적, 오류 목록이나 달력 오류가 있는 결과도 저장하지 않습니다. Statcast 시즌 요약과 사용자가 요청한 선수·날짜 구간만 저장합니다. 선택 구간의 투구 행은 기존 분석을 재현하고 재다운로드를 피하기 위한 것이며 MLB 전체 투구를 자동 수집하지 않습니다. 원본 행·표본 수·분모·중복 제거·계산 정의는 유지했습니다. Parquet 등 새 의존성은 추가하지 않았습니다.

화면 하단의 출처·갱신 시각 펼치기에서 현재 실행에 관측된 서비스의 메모리·SQLite·원본 조회 여부를 볼 수 있습니다. 별도 펼치기는 전체 DB의 최근 항목이며 현재 화면 자료와 다를 수 있다고 표시합니다. 기존 UI가 서비스 자체를 호출하지 않고 세션에 보관한 결과를 바로 표시하는 경우에는 기존 조회 시각과 경고를 확인해야 합니다.

인터넷이 끊겨도 **유효한 SQLite 자료**는 사용할 수 있습니다. 만료 자료를 대신 반환하는 기능은 넣지 않았으므로, 만료되었거나 저장되지 않은 자료는 기존 API 오류 안내가 표시됩니다. SQLite 문제가 발생하면 경고하고 원본 API 조회를 시도하며, 기존 데이터를 삭제하거나 손상된 DB를 자동 초기화하지 않습니다. Ollama 경로는 변경하지 않아 통계 조회와 계속 분리됩니다.

## 7. 테스트

전체 자동 테스트 명령:

```powershell
$env:MLB_CACHE_DISABLED='1'
.\.venv-test\Scripts\python.exe -m unittest discover -s tests
Remove-Item Env:MLB_CACHE_DISABLED
```

기존 모의 API 회귀 테스트는 영구 캐시를 끄고 실행합니다. 새 DB 테스트는 자체적으로 캐시를 켜고 임시 DB를 지정합니다. 실제 DB나 즐겨찾기에 대한 파괴 테스트는 하지 않습니다. 새 테스트는 초기화·버전 거부·인덱스·트랜잭션 롤백·고유 키·선수 ID·기간/범주/경기 범위 구분·만료·누락/부분 결과·API 실패·동시 접근·무결성·백업/복구·설정 보존·메모리/SQLite 관찰·개발자 화면 숨김·한영 표시를 검사합니다. 별도 프로세스 재시작 지속성은 벤치마크에서도 검증했습니다. JSON을 이전하지 않으므로 즐겨찾기 마이그레이션 대신 원본 보존을 검사합니다.

전체 자동 테스트 **234개가 통과**했습니다. 기존 회귀 테스트는 검색·타자/투수/겸업·통계·고급 지표·리그 평균·Statcast·순위/유사 선수·커리어·비교·수상·리더보드/필터·AI·즐겨찾기·언어와 모듈 구조를 포함합니다. 결과 로그는 `v48-test-results.log`를 확인하세요. 실제 Ollama 및 모든 실시간 API를 대상으로 한 종합 검증은 수행하지 않았습니다.

`scripts.check_startup`의 Streamlit health 검사와 `scripts.check_launcher`의 실제 Windows `start.bat` 실행 검사는 통과했습니다. health 응답은 서버 실행 확인이며 모든 화면의 브라우저 렌더링 검증을 뜻하지 않습니다.

## 8. 실행·관리 화면

평소에는 기존처럼 **`start.bat`을 실행**하세요. 유료 API나 새 설치 과정은 없습니다.

개발자 관리 화면을 사용하려면 새 PowerShell에서 다음과 같이 실행합니다.

```powershell
$env:MLB_ANALYTICS_DEVELOPER='1'
.\start.bat
```

사이드바의 **시스템 상태 / System Performance**를 선택하세요. 기본 상태에서는 이 메뉴가 없습니다. DB 크기·선수/팀/캐시 건수·출처·수집/만료 시각·실제 적중/실패·서비스 조회 시간을 표시합니다. 측정은 프로세스 시작 또는 초기화 버튼 이후이며 재시작하면 초기화됩니다. `hit_rate`는 SQLite, `overall_hit_rate`는 메모리를 포함합니다. `source_error`는 서비스 조회 실패이며 개별 HTTP 오류 개수와 같지 않습니다. 아직 측정하지 않은 비율·시간은 빈 값으로 표시합니다. 경로·자격증명·원본 예외 상세는 화면에 노출하지 않습니다. 이 환경변수는 로컬 개발자 기능 표시용이며 공개 서버의 접근 인증 수단은 아닙니다.

기존 **기록 새로고침**은 통계 캐시를 만료시키고 메모리를 비운 다음 필요한 자료를 다시 요청합니다. 개인 설정은 건드리지 않습니다. 관리 화면의 정리는 기본적으로 만료 항목만 삭제하며, 체크박스 확인이 있어야 실행됩니다.

## 9. 백업·복구

관리 화면의 **DB 백업 생성**은 SQLite 공식 backup API를 사용하고 무결성 검사까지 수행합니다. 결과는 DB 폴더 안 `backups`에 새 파일로 생성되며 기존 백업을 덮어쓰지 않습니다. 실행 중 DB를 파일 복사하는 방식을 사용하지 않습니다.

복구할 때:

1. 앱을 완전히 종료합니다.
2. 현재 DB를 삭제하지 말고 별도 이름으로 보관합니다.
3. 복구할 백업의 무결성을 확인합니다. 프로젝트에서 `python -c "from services.database import integrity; print(integrity(r'백업파일의 전체경로'))"`를 실행하면 됩니다. 실제 가상환경 Python을 사용하세요.
4. 검증 결과가 `ok`인 백업 파일을 기본 DB 경로의 `mlb_analytics.db`로 복사합니다. 현재 DB를 보관한 뒤 앱이 종료된 상태에서만 수행합니다.
5. 앱을 실행하고 관리 화면에서 무결성과 건수를 다시 확인합니다.

즐겨찾기·설정·프리셋 JSON은 DB 백업에 포함되지 않습니다. 이 파일들은 `data` 폴더 또는 기존 `MLB_ANALYTICS_DATA_DIR`에서 별도로 백업하세요. 코드 전체를 되돌릴 필요가 있으면 변경 전 `.backups` 폴더의 파일을 사용하며, 사용자 데이터는 복구 시점 이후 변경 내용을 먼저 보관해야 합니다.

## 10. 남은 제한

- 실제 인터넷 속도 개선 수치는 없습니다. 검증된 효과는 앱 재시작 후 저장된 데이터로 원본 호출을 생략하는 것입니다.
- 현재 연도 시즌 종료 후에도 보수적으로 15분 TTL을 유지합니다. 공식 달력 기반의 시즌 종료 자동 장기화는 하지 않았습니다.
- 통계 캐시를 자동 삭제하지 않습니다. 사용자가 많은 선수의 투구 구간을 저장하면 용량이 늘어날 수 있으므로 관리 화면에서 확인 후 정리하세요.
- 만료 데이터의 오프라인 대체 반환은 지원하지 않습니다. 유효한 과거 데이터만 오프라인에서 재사용합니다.
- 단일 프로세스의 Streamlit 메모리 중복 억제는 유지하지만 여러 앱 프로세스가 동시에 동일한 최초 요청을 하면 원본 API를 각각 호출할 수 있습니다. DB 고유 키는 중복 저장을 방지합니다.
- 모니터링은 연결한 서비스 단위이며, Ollama·이미지·개별 HTTP 전송을 모두 추적하는 네트워크 계측 시스템은 아닙니다.
